# v1.39.0 — Recall at large budgets, multi-session aggregation, a Chinese gate, and a memory fix

## Highlights

- **Bounded memory at scale.** Resident memory no longer grows with the number of ingested turns. The SQLite driver (`@photostructure/sqlite`, 1.2.1 and 3.3.0 alike) keeps about 4.6 KB of native memory for every prepared statement that binds text, through garbage collection and `close()`, and Mnemora prepared a statement on every call (28,910 prepares from 92 distinct SQL strings for 2,000 turns). Resident memory grew about 65 MB per 1,000 turns: 6.8 GB after 100k turns for a 271 MB database. Each connection now caches its prepared statements by SQL text (least recently used evicted past 512). At 100k turns: resident memory 6.8 GB → 388 MB, recall p95 465 → 172 ms at 800 tokens and 573 → 275 ms at 4000 tokens, ingestion 750 → 967 turns/s.
- **Adaptive fill at large recall budgets.** At `tokenBudget` 1600 or more, records held back only by the admission score (at least 0.7 of it) fill the room admitted records leave, through the same anchor and admission rules, once an admitted record matches the prompt well (query match 0.35 or more). New option `unifiedRetrieval.adaptiveFill`, on by default. The default budget (800) is unchanged and unaffected.
- **Multi-session aggregation.** For "how many / in total" prompts: plural prompt anchors also match their singular ("weddings" finds "wedding"); assistant replies are no longer recalled for aggregate prompts (322 of 323 multi-session evidence turns in LongMemEval_S are the user's, and replies filled the budget), except look-backs such as "can you remind me … the average", which keep them demoted; at a fill budget an aggregate prompt searches 80 conversation records instead of 40.
- **A Chinese retrieval gate.** CI now also runs the gate's 100 questions on a reduced LongMemEval_S subset translated to Chinese, at 800 and 4000 tokens (dataset in the repository, 1.8 MB, MIT notice). All four gates also count `allEvidenceTurns`: evidence found through the labelled turn itself, not through any record of the same session.

## Results (LongMemEval_S, lexical, no embeddings)

Questions with all evidence recalled, 500 questions:

| Budget | v1.38.0 | v1.39.0 | Multi-session | Mean tokens |
|---|---|---|---|---|
| 800 tokens, 8 records | 73.8% | 75.1% | 52.9% → 57.9% | 635 → 600 |
| 4000 tokens, 20 records | 78.5% | 83.0% (bm25 81.1%) | → 76.0% (bm25 68.6%) | 1,980 (bm25 3,687) |

Question answering at 4000 tokens (reader and judge `mimo-v2.6-pro`, official prompts), measured with adaptive fill before multi-session aggregation: Mnemora 79.6% with 3,127 context tokens, bm25 77.6% with 3,924 (exact binomial p = 0.22, not a significant margin). Multi-session aggregation then raised the multi-session answerable questions from 61.2% to 68.6% (bm25 61.2%; 14 newly right, 3 newly wrong, p = 0.013) with 1,494 tokens on average, and multi-session abstention from 83.3% to 100%.

Chinese gate, same 100 questions, by labelled evidence turns: 56 at 800 tokens and 61 at 4000, against 63 and 69 for the same reduced subset in English.

## Behaviour changes (please read before upgrading)

1. **Recall at budgets of 1600 or more returns more records.** Adaptive fill is on by default. Set `unifiedRetrieval.adaptiveFill: false` to keep the 1.38.0 behaviour. At the default budget nothing changes.
2. **Aggregate prompts no longer recall assistant replies**, at any budget, except look-back prompts ("remind me", 提醒我), where they stay demoted below the user's turns.
3. **Statements are shared per connection.** `openMnemoraDatabase` returns a connection whose `prepare(sql)` returns the same statement object for the same SQL text. Mnemora itself uses no `iterate()` and no per-statement option setters. Library users who call `openMnemoraDatabase` directly and change options on a returned statement (for example `setReadBigInts`) will see that setting on later `prepare` calls of the same SQL.
4. **No schema migration (still v88).** Existing databases open unchanged; earlier releases can still read them.

## Tried and not shipped

- **Fact supersession.** On the 72 answerable knowledge-update questions Mnemora answers 93.1% at 800 tokens and 91.7% at 4000. Linking only to the user's later statements, with or without firmer guidance, moved nothing beyond noise. In four of the seven misses at 4000 both values were in the packet and the reader still chose the older one. A real validity window needs facts extracted with values at write time; not scheduled.

## Known limits

- Chinese trails English by 7–8 of 100 questions on the gate. One visible cause: the adaptive-fill threshold (0.35) was set on English query match, and Chinese prompts match lower (about 0.2), so fill rarely opens for them.
- Preference questions at large budgets recall less evidence than bm25 (66.7% against 73.3%), although QA at 4000 tokens is level or ahead (63.3% against 60.0%, 30 questions).
- The QA numbers are from one reader and judge model (`mimo-v2.6-pro`); the overall 4000-token QA margin over bm25 is not significant.
- `scripts/benchmark-recall-scale.mjs` measures latency and memory on synthetic turns and is not part of CI; wall-clock numbers depend on the machine.

Mnemora 1.39.0 主要改进大预算召回，并修复了一个内存问题。SQLite 驱动每准备一条语句就留下几 KB 原生内存，而 Mnemora 每次调用都重新准备语句，导致内存随写入量线性增长（10 万轮对话时 6.8 GB）；现在每个连接按 SQL 文本缓存语句，10 万轮时内存降到 388 MB，召回 p95 在预算 800 / 4000 下分别降到 172 ms / 275 ms。预算 1600 及以上时新增自适应补充召回（`unifiedRetrieval.adaptiveFill`，默认开启，默认预算 800 不受影响）；"一共多少"类统计问题改进了复数匹配、不再召回助手回复（"提醒我"类回顾除外），并在大预算下扩大候选池。LongMemEval_S 500 题证据全召回率：预算 800 从 73.8% 到 75.1%，预算 4000 从 78.5% 到 83.0%（bm25 81.1%），用的 token 更少。CI 新增中文检索门禁，所有门禁增加"证据轮"指标。无数据库迁移。升级前请阅读 "Behaviour changes"：大预算召回的记录会变多，统计类问题不再召回助手回复，`openMnemoraDatabase` 返回的连接会复用同一 SQL 的语句对象。
