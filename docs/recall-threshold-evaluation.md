# Recall threshold evaluation

This is an operator evaluation tool, not an automatic calibration service.
It evaluates **manual unified retrieval's adjusted-score floor** against a
labelled corpus. It does not evaluate model continuation, automatic injection,
embedding quality or every graph-ranking parameter.

## Parameter inventory

| Parameter | Current default | Actual role |
| --- | --- | --- |
| `unified.hardMinScore` | `.35` | Per-request adjusted-score floor in `src/retrieval/service.ts`, before candidate/budget packing. The scan supports only this parameter; it is not a plugin configuration key. |
| `recall.semanticMinScore` | `.35` | Semantic recall cutoff; a different score surface from unified ranking. |
| `recall.injection.minRelevanceScore` | `.72` | Injection lifecycle relevance gate, configured in `src/config.ts`. |
| Graph supplement semantic floor | `.72` | Separate fixed safeguard in `src/retrieval/injection-policy.ts`. |
| `quality.relatedToMinConfidence` | `.85` | Relation admission confidence, not retrieval relevance. |
| `unifiedRetrieval.diversityLambda` | `.75` | MMR diversity weight for automatic context selection. |
| `quality.rankingWeights.ppr` | `.15` | Configurable PPR contribution to quality ranking. |

The documented `0.3×` PPR comparison is a topology-assessment perturbation,
not the production PPR ranking weight. Do not consolidate these unlike
quantities into one threshold. This increment changes none of their defaults.
`tests/fixtures/hybrid-retrieval.json` and the release benchmark are synthetic
contract fixtures, not labelled evidence for the production embedding model.

## Prepare an authorized experiment

Use a separate, explicitly authorized corpus snapshot, not a live production
database. Retain its identity, labels and review provenance in the authorized
workspace. The plan contains queries, scopes and canonical references and is
therefore **not** automatically safe to publish. No production data is needed
to run the synthetic regression.

Freeze the plan before running. Its JSON object has these fields:

```json
{
  "version": 1,
  "evidenceKind": "operator_reviewed",
  "parameter": "unified.hardMinScore",
  "thresholds": [0.2, 0.35, 0.5, 0.7],
  "tokenBudget": 800,
  "candidateLimit": 10,
  "operationTimeoutMs": 2000,
  "deadlineMs": 60000,
  "selection": { "minPrecision": 0.8, "minRecall": 0.8, "maxP95LatencyMs": 1000 },
  "tuning": { "version": 1, "id": "study.tuning", "cases": [] },
  "test": { "version": 1, "id": "study.test", "cases": [] }
}
```

The empty case arrays above are placeholders, **not a runnable experiment**.
Populate each with existing `EvaluationCase` objects: `id`, `kind`, `scope`,
`query`, `expectedRefs`, optionally `forbiddenRefs`, `topK` and `cohort`.
Each split requires 2–100 cases, a positive case, and an explicit empty-recall
or scope-isolation negative control. IDs must be disjoint across splits;
normalized scope/query identities cannot repeat within or across them. Queries
longer than the retrieval surface's 512-character limit are rejected, not cut.

At least five cases and two positives per split are required for `reviewable`.
This is only a coverage guard, **not statistical power or efficacy proof**.
Independence of histories/tasks and adequacy of labels require operator review;
different query strings alone do not establish independence. `operator_reviewed`
is an operator assertion, not a certification generated by the tool.

## Run

After building with the repository-supported Node version:

```sh
MNEMORA_DB=/authorized/workspace/corpus-snapshot.db node dist/cli.js evaluate recall-threshold-scan /authorized/workspace/scan-plan.json
```

In PowerShell, set `$env:MNEMORA_DB` to the snapshot before the same invocation.
The database must explicitly exist and match schema 83. The command opens a
native read-only connection, skips normal store initialization/migrations,
holds one read transaction, and fixes the scoring clock for the whole scan.
An absent path, `:memory:`, an unspecified database or another schema fails
without creating or upgrading a database. Retain the snapshot externally:
the output's plan hash does not fingerprint database contents.

## Frozen selection and report

1. Evaluate every planned tuning threshold in ascending order, applying the
   threshold before the existing candidate and budget packing.
2. Any failed/invalid/unsafe tuning run withholds selection. Eligible values
   must satisfy positive-case macro precision and recall, all negative controls,
   zero forbidden/cross-scope/invalid references, estimated-token budget and
   the preregistered p95 retrieval-latency limit.
3. Select by F1 (harmonic mean of those macro precision/recall metrics), then
   lower average estimated tokens, then higher threshold. Latency is a gate,
   not a noisy tie-breaker. Evaluate **only that value** on held-out test.
4. A held-out failure withholds review; it never triggers reselection. A new
   selection rule or grid needs a new registration and fresh held-out evidence.

The aggregate report includes a normalized-plan SHA-256, tuning curves,
selection and held-out metrics; no queries, scopes, references, case IDs or
database paths. Tokens are the project's retrieval-envelope estimates, **not
model usage or a final automatic prompt measurement**. Latency covers retrieval
execution, not end-to-end model response time. Cancellation/deadline/provider
failures cannot become successful evidence. Blocking synchronous retrieval
cannot be preempted by an event-loop timer; its elapsed overrun is rejected
after return rather than counted as successful evidence. This boundary is not
a hard wall-clock termination guarantee for arbitrary injected adapters.

Even a clean `reviewable` report states `deploymentApproval="not_granted"`
and `automatedPolicyChange="not_performed"`. Synthetic evidence is always
withheld. The scan does not edit configuration, migrate vectors, change schema
or authorize deployment. `npm run benchmark:recall-quality` exercises a frozen
fictional corpus and six thresholds solely as a repeatable regression.
